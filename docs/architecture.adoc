= oxmonad architecture
:toc: left

oxmonad is an xmonad-style tiling window manager for Wayland. It is **not** a
compositor: it runs as the window-manager client of
https://codeberg.org/river/river[river] 0.4+, speaking the stable
`river-window-management-v1` protocol. river owns DRM/KMS, input devices,
rendering, xdg-shell, layer-shell, screencopy, session lock and Xwayland;
oxmonad owns every policy decision: which windows are visible, where they go,
which one has focus, keybindings, borders, and the bar/prompt/layout
picker/tab-strip UI, including a system tray.

Everything oxmonad ships is Rust. river (Zig) is an external runtime
dependency, packaged on Arch as `river`.

== Crates

[cols="1,3"]
|===
| Crate | Responsibility

| `crates/oxmonad-core`
| Pure window-management model. No Wayland, no I/O, no clocks. xmonad's
  `StackSet`, the layout ring, manage rules, the prompt, layout picker and
  key binding help state machines, actions
  and the TOML config schema. Everything here is unit-tested.

| `crates/oxmonad-ui`
| Pure software drawing of the WM-owned surfaces (bar, prompt, layout picker,
  key binding help, tab strip, the solid divider between virtual screens) into
  pixel buffers with `tiny-skia`, `skrifa` and `zeno`. Knows nothing about
  windows or Wayland; takes plain view structs. Golden-image tests live here.

| `crates/river-protocols`
| `wayland-scanner`-generated client bindings for the river protocols
  (`protocols/*.xml`, copied verbatim from river v0.4.8).

| `crates/oxmonad`
| The binary. Connects to river, mirrors river's objects (windows, outputs,
  seats) into core IDs, translates protocol events into core calls and core's
  `Arrangement` into protocol requests, owns the wl_shm shell surfaces the UI
  crate draws into, spawns processes, reads the config file, drives the
  clock/battery bar modules and hosts the system tray on D-Bus.
|===

Dependency direction: `oxmonad` → `oxmonad-core`, `oxmonad-ui`,
`river-protocols`. `oxmonad-core` and `oxmonad-ui` do not depend on each
other; the binary converts core models into UI view structs. The tray is
binary-only: tray items are not a window-management concept, so core never
sees them.

== The river protocol loop

river drives two kinds of sequences (see the `river_window_manager_v1`
description in `crates/river-protocols/protocols/river-window-management-v1.xml`):

. **manage sequence** (`manage_start` … `manage_finish`): may change window
  management state — dimensions (`propose_dimensions`), `show`/`hide`,
  keyboard focus (`river_seat_v1.focus_window` / `focus_shell_surface`),
  fullscreen, borders, key/pointer bindings.
. **render sequence** (`render_start` … `render_finish`): may change only
  rendering state — node positions (`river_node_v1.set_position`), stacking
  (`place_top`/`place_above`…), decoration offsets, borders.

oxmonad's binary follows one rule: **core state only changes in response to
events; requests are only derived from core state.** Concretely:

* Events outside a sequence (new window, title change, key binding
  `pressed`, pointer op deltas, output added…) are recorded into the model
  and, if they carry user intent (a key press), queued as `Action`s. If an
  action is queued while idle, the binary sends `manage_dirty`.
* On `manage_start`: drain queued actions into core, call
  `Wm::arrange()`, and emit all window-management requests from the
  resulting `Arrangement`, then `manage_finish`.
* On `render_start`: using the dimensions river reported, emit positions and
  stacking for every visible window and shell surface from the last
  `Arrangement`, then `render_finish`. Tiled windows are centred in their
  slot if the client chose a smaller size than proposed; a client larger
  than its slot (one that will not shrink below its minimum size, like a
  browser in a narrow column) is clipped to the slot with
  `set_content_clip_box` (river 0.4's protocol version 3), so it neither
  covers its neighbours nor crosses a screen or divider, and river draws
  its border around the visible part.

== Core model (`oxmonad-core`)

Identifiers are opaque newtypes: `WindowId(u64)` and `OutputId(u64)` are
assigned by the binary, `ScreenId(u64)` by core (an output's first screen is
`ScreenId(output)`; see <<Virtual screens>>). Geometry is `Rect { x, y, w, h: i32 }` in
river's logical coordinate space.

=== StackSet

A direct port of xmonad's `StackSet` semantics:

* `Stack<W> { focus, up: Vec<W>, down: Vec<W> }` zipper.
* `Workspace { tag: String, layout: LayoutRing, stack: Option<Stack> }`.
* `Output { id, name, rect, usable }` — one per river output.
* `Screen { id, output, workspace, region, rect, usable_rect }` — `current`
  plus `visible`; `region` is the part of the output the screen covers;
  remaining workspaces are `hidden`, ordered most-recently-hidden first
  (drives `toggleWS`).
* `floating: HashMap<WindowId, RationalRect>` — floats are stored relative to
  their screen (xmonad's `RationalRect`), so they follow the workspace across
  screens of different size.
* Invariant (tested): every managed window is in at least one workspace; a
  window may be in several workspaces (`CopyWindow`) and is removed from all
  on unmanage. When a copied window is visible on several screens, it is
  placed on the first such screen in screen order and the focused screen
  wins.

=== Layouts

Layouts are pure functions `arrange(&self, area: Rect, n: usize, focus: usize)
-> Vec<Rect>` plus `handle(&mut self, LayoutMessage) -> bool`. The ring from
`resources/xmonad.hs`:

`reflectHoriz tiled ||| tiled ||| Mirror tiled ||| noBorders Full |||
tabbed ||| Mirror Grid ||| Grid ||| ThreeCol ||| reflectHoriz ThreeCol`,
followed by oxmonad's own `Corner` and `reflectHoriz Corner`, with
`tiled = ResizableTall 1 (3/100) (3/5) []` and `ThreeCol 1 (3/100) (1/2)`.

In code these are the `standard_layouts` (`LayoutRing::standard`): `Tall
Right`, `Tall`, `Wide`, `Full`, `Tabs`, `Grid Rows`, `Grid`, `Three
Columns`, `Three Columns Right`, `Corner`, `Corner Right`, built from the `Layout` variants
`Tall`, `ThreeColumns`, `Corner`, `Grid`, `Full`, `Tabbed` and the
modifiers `Mirror`, `Reflect` and `NoBorders`. `Layout::name` is both the
bar text and the identity used when restoring a saved ring; a saved ring
that no longer parses (layouts renamed or removed) only resets that
workspace's layouts, the rest of a restart snapshot still applies.

The config's top-level `layouts` list picks and orders the ring: config
loading resolves the names (matched against `Layout::name` ignoring case)
into a validated `LayoutOrder` (indices into `standard_layouts`; empty
lists, unknown and duplicate names are `ConfigError::InvalidLayouts`, whose
message lists the valid names), and `LayoutRing::from_order(order,
tabs.height)` builds the ring from the standard layouts with their standard
parameters. Its first entry is every workspace's default layout. The
default config lists all ten in the standard order. The layout picker and
its `1`–`9`/`0` keys follow ring order, so they follow the config too.

Each ring entry keeps its own state; `NextLayout` rotates, `ResetLayout`
rebuilds the ring from config (`StackSet::layout_template`). On a reload
(`Wm::reconfigure`) `StackSet::set_layout_template` reconciles every
existing workspace's ring with the new one through `LayoutRing::restore`,
the same rule a restart uses: an unchanged list of layouts keeps every
entry's state (only `Tabs` takes the new `tabs.height`); a reordered or
shortened list replaces the ring, keeping the active layout active if it is
still listed and starting at the first entry otherwise. A reload also
closes an open layout picker, whose entries may have moved. Messages: `Shrink`, `Expand`,
`IncMasterN(i32)`, `MirrorShrink`, `MirrorExpand`. Integer rounding must
match xmonad (ported from the Haskell sources in `resources/`).

=== Wm facade

`Wm` bundles the `StackSet`, per-window info (`app_id`, `title`,
`has_parent`, fullscreen flag), rules, config-derived settings and the
prompt. The binary talks to core only through `Wm`:

* outputs: `add_output`, `remove_output`, `set_output_rect`,
  `set_usable_rect` (screens follow from outputs and splits)
* windows: `manage(id, info)` (runs manage rules), `unmanage`,
  `update_info`, `request_fullscreen(id, bool)`, `focus_window(id)`
  (click / pointer focus), `float_at(id, rect)`, `set_float_rect(id, rect)`
* input: `apply(Action) -> Vec<Effect>`; `prompt_key(PromptKey) -> Vec<Effect>`
  (to the prompt, the layout picker or the help, whichever is open:
  `grabs_keyboard()`); `pick_layout(index)` (a clicked picker card),
  `close_help()` (a click on the help), `set_help_viewport(page, max)`
* output: `arrange() -> Arrangement`, plus view models for each output's
  bar (`bar_model(output)`), prompt (`prompt_model()`), layout picker
  (`layout_picker_model()`), help (`help_model()`) and tab strips.
* restart: `snapshot(id_of) -> Snapshot`, `restore(Snapshot)`,
  `manage_as(id, identifier, info)`, `finish_restore()` (see
  <<Restart in place>>).

`Effect` is everything core wants the outside world to do:
`Spawn(String)`, `Close(WindowId)`, `Quit`, `Reload`, `Restart`,
`StartPointerMove(WindowId)`, `StartPointerResize(WindowId)`,
`WarpPointer`… The binary executes effects; core never performs I/O.

`Arrangement` describes the whole desired state:

* `windows`: bottom-to-top list of `Placement { window, screen, output,
  rect, layer: Tiled | Floating | Fullscreen | VirtualFullscreen, border:
  Option<Border> }` for every visible window;
* `hidden`: managed windows to hide;
* `focus`: `Focus::Window(id) | Focus::Prompt | Focus::LayoutPicker |
  Focus::Help | Focus::None`;
* `screens`: per screen its output and its tab strip (rect + tabs) when the
  layout is `tabbed`;
* `bars`: every bar that is shown, in bar order, as `BarPlacement { output,
  rect, primary }` (`primary`: the bar with the tray, battery and clock);
* `dividers`: the lines between virtual screens, `Divider { output, rect,
  color }`, by output and then in screen order (see <<Virtual screens>>).

=== Layout picker

`pick-layout` opens (or, when open, closes) a picker over the current
workspace's ring; opening the prompt closes it and vice versa. The pure
`LayoutPicker` (`layout_picker.rs`) holds the workspace tag and the
selection (initially the active layout) and maps `PromptKey`s: `j`, `Down`,
`Right`, `Tab` next and `k`, `Up`, `Left`, `Shift+Tab` previous (wrapping),
`Return`/`space` apply, `1`–`9`/`0` apply directly, `Escape` cancels.
Applying calls `LayoutRing::select(index)`, which keeps every layout's
state. Each entry's picture is `Layout::preview()`: the layout arranging
four windows in the 16:9 `PREVIEW_AREA`, the same helper that generates
`docs/layouts/*.svg`, so the picker and the docs cannot disagree.
`Arrangement.layout_picker` is the picker's screen and the usable area the
binary centres it in.

=== Key binding help

`help` (`Mod+Shift+/`, xmonad's default help) toggles an overlay listing
every active key and pointer binding; it is exclusive with the prompt and
the layout picker. `help::help_groups(&Config)` builds its content from the
resolved config (so user overrides, removals and the modifier show as
bound): key bindings are grouped by what their action does (Launch,
Windows, Layouts, Workspaces, Screens, Session), pointer bindings under
Mouse, ordered by action kind and then combination. The pure `Help` state
holds the scroll offset in rows: `j`/`k`/arrows scroll by a row,
`PageUp`/`PageDown` by a page, `Home`/`End` to either end, `Escape`, `q`
and `Return` close. Only the renderer knows how many rows fit, so the
binary reports them each manage sequence (`set_help_viewport`), which
clamps the offset. `Arrangement.help` is the current screen and its usable
area.

== UI (`oxmonad-ui`)

Draws premultiplied ARGB8888 (`wl_shm` `argb8888`, little-endian) buffers at
an integer scale. Inputs are plain view structs (`BarView`, `PromptView`,
`LayoutPickerView`, `MenuView`, `TabsView`, `Theme`). The layout picker is a grid of
cards (up to five per row, shrunk to fit the screen), each a preview drawn
in the docs pictures' colors above the layout's name; `picker_entry_at`
hit-tests clicks against the same geometry. The help overlay lays out a
key and an action column per binding under section headings and flows the
sections into the fewest columns that fit the screen height (as many as
the width allows, then scrolling, with a scroll bar); `help_viewport`
reports the visible rows and the scroll limit from the same layout. A bar
`Segment` can be an `Icon` (premultiplied BGRA pixels in a shared `Arc`, so
views stay cheap to clone and compare) instead of text, e.g. a tray item: it
takes a `BarStyle::icon_size` square plus `icon_spacing` on either side, the
icon fitted into it keeping its aspect ratio (area-averaged when shrinking,
bicubic when enlarging) and vertically centered. `BarLayout::segment_at`
hit-tests icon segments like text ones and `BarLayout::segment_span` reports
where a segment landed, to anchor a popup under it. A segment can also be
a `LayoutGlyph`, a miniature of the current layout drawn before its name
(`[bar] layout_icon`): the layout's `preview()` rectangles (the same ones
the layout picker and `docs/layouts/*.svg` draw) scaled to
`BarStyle::layout_icon_size` (14) high at the preview's 16:9 ratio, snapped
to device pixels with a pixel gap per scale step between windows, the
master and its tab in the segment's color and the other windows and tabs
fainter. A tab strip keeps at least 4 px, the windows below it sharing the
rest, so Tabs does not shrink to Full's plain block.
`BarModel::layout_preview` carries the preview from core. The popup menu
(`MenuView`, `render_menu`) is a bordered column of rows: plain, disabled
(dimmed), separator, check box or radio entries, with an arrow on entries
that open a submenu; it is as wide as its widest label up to
`MenuStyle::max_width` (labels are ellipsized beyond that) and
`menu_entry_at` hit-tests the same geometry, skipping separators and
disabled entries. Glyph outlines come from `skrifa`, hinted by its
automatic hinter in normal (full) mode so stems snap to whole pixels, with
advances and the pen position rounded to whole pixels; `zeno` rasterizes
them. `[font] antialias` selects grayscale or subpixel (`rgb`/`bgr`,
filtered with FreeType's default LCD filter) coverage; subpixel glyphs are
only drawn in opaque colors over opaque pixels, anything else falls back to
grayscale. The default font is Fira Mono embedded from
`assets/FiraMono-Regular.ttf` (SIL OFL, see `assets/FiraMono-LICENSE.txt`),
so renders are deterministic across machines. A config asking for "Fira Mono"
uses the embedded font without looking at the installed ones; any other
family is found via `fontdb`, which scans every installed font file (~85 ms
with thousands of fonts). The binary (`crates/oxmonad/src/font_cache.rs`)
remembers the file it found in `$XDG_CACHE_HOME/oxmonad/fonts` and only
scans again when that file is gone, keeping startup and restarts fast.

== Configuration

`$XDG_CONFIG_HOME/oxmonad/config.toml`, merged over the defaults embedded
from `crates/oxmonad-core/default-config.toml` (the single source of truth for
default keybindings, colors, commands and rules). `SIGUSR1` (or the
`reload` action) reloads it; `Mod+q` restarts oxmonad, which reads it anew.
The user-facing reference for every setting, the merge rules and the actions
is link:config.adoc[`config.adoc`].

== Core implementation notes (deviations)

Where `oxmonad-core` differs from or refines the contract above:

* **Headless state.** xmonad always has a screen; river may start with none.
  Until the first output appears (and after the last one disappears) the
  `StackSet` keeps its current workspace on a placeholder screen that
  `screens()` never reports, so every operation behaves uniformly.
  Outputs carry their `name` (`add_output(id, name, rect)`), used to pick
  the bars (`bar.output`, `bar.primary`).
* **View semantics.** `view <tag>` (`Mod+1..9`, the prompt) is xmonad's
  `greedyView`, as in xmonad's default keys and `selectWorkspace`;
  `focus-screen` / `toggle-ws` use plain `view`. `view` never creates
  workspaces; the prompt does.
* **Placements.** `Placement.rect` is the window *content* rectangle; the
  border is drawn outside it, so content plus border fill the layout slot
  (xmonad's `tileWindow`). `float_at` / `set_float_rect` also take content
  rectangles. `Full` and `tabbed` place only the focused window; the others
  are listed in `Arrangement.hidden`. `Arrangement` additionally carries
  `prompt: Option<(ScreenId, Rect)>`.
* **Smart borders.** `[border] smart` ports `XMonad.Layout.NoBorders`:
  `single-screen` (`smartBorders`, i.e. `lessBorders Never`) drops the
  border of a tiled window its layout places alone while
  `StackSet::screens()` has exactly one screen (a split output counts as
  several); `per-screen` (`lessBorders Screen`) drops it on any screen,
  so the divider between virtual screens (see <<Virtual screens>>) is what
  keeps their borderless lone windows apart. Both
  drop the border of a float whose content covers its screen's rectangle,
  keeping the float's content rectangle. A borderless tiled window fills its
  whole slot.
* **Bar model.** Every output gets a bar (where xmobar needs one process
  per screen); `bar.output` (a list of names, unconnected ones skipped, `[]`
  for none) restricts them, and `Wm::bar_outputs` lists them in bar order:
  the list order, else `StackSet::outputs()` order. The primary bar
  (`Wm::primary_bar_output`) is the `bar.primary` output if it has a bar,
  else the first bar output; toggling it off does not move the primary
  role. Each bar spans the usable width of its output (like xmobar's
  strut), across the virtual screens of a split output. The screen that
  speaks for an output's bar (`Wm::bar_screen`) is the current screen if it
  is on that output, else the output's first screen: its workspace decides
  the bar's `toggle-bar` visibility (`Wm::bar_shown_on`) and supplies the
  layout and title of `bar_model(output)`; the workspace tags and their
  states are the same on every bar. `tiling_area` only subtracts the bar of
  the screen's own output (and the dividers between it and the other virtual
  screens of that output). A workspace click on a bar first makes that
  bar's screen current (`Wm::focus_bar_screen`), so the workspace is viewed
  on that output.
  Workspace order follows `getSortByIndex`: configured tags in config order,
  then the rest sorted by tag. The scratchpad workspace (`NSP`) is excluded
  from the bar, prompt completion, `toggle-ws`, screen assignment and
  `remove-workspace` targets.
* **Copies.** Shifting a window that has copies elsewhere still inserts it
  into the target (xmonad's `insertUp` would silently drop it).
* **Window info.** `WindowInfo` has an optional `preferred_size`, used to
  centre floating transients; without it they take the middle quarter of the
  screen.
* **Effects.** No `WarpPointer` effect: xmonad does not warp by default.

== Binary implementation notes

How `crates/oxmonad` realises the protocol loop above:

* **Modules.** `state` (the mirror of river's objects and the two
  sequences; `state/dispatch.rs` records events), `plan` (pure
  `Arrangement` → request translation behind the `Requests` trait, diffed
  against what river was last told), `shell` + `shm` (bar, tab strips, dividers,
  prompt, layout picker, help and tray menu as `river_shell_surface_v1`s in memfd-backed `wl_shm` buffers),
  `keys` / `keyboard` (keysym resolution and the prompt's keyboard via the
  pure-Rust `kbvm`), `status` (clock and battery), `tray` (the
  `StatusNotifierItem` host on its own thread), `tray_ui` (pure: tray items
  as bar icons, click mapping, the open menu's state, layout and placement),
  `control` (the `OXMONAD_CONTROL` socket), `remote` (`oxmonad --restart`),
  `spawn`, `restart` (saving the snapshot and re-executing).
* **Shell surfaces are redrawn in the manage sequence**, not the render
  sequence: their content only depends on core state, and committing them
  (with `sync_next_commit`) during the manage sequence maps the prompt before
  river applies `focus_shell_surface`. The render sequence repositions and
  restacks them with the windows.
* **Stacking.** Tiled and floating windows bottom to top, then the bars (one
  shell surface per output, `Node::Bar(output)`, drawn at that output's
  scale), tab strips and the dividers between virtual screens
  (`Node::Divider(output, index)`, a `wl_shm` buffer filled with
  `split.divider_color` by `oxmonad_ui::render_fill` at the output's scale;
  clicks on them do nothing), then fullscreen windows (which therefore cover
  the bars and dividers), then the
  prompt, layout picker or help, then the tray menu and its submenus.
* **Input ordering.** Key/pointer binding presses, clicks, pointer enters and
  control commands are queued and applied in order at `manage_start`.
  Clicks on shell surfaces come from oxmonad's own `wl_pointer` (one per
  seat), which knows the button and the exact surface position, not from
  `river_seat_v1.shell_surface_interaction` (ignored, so nothing is
  handled twice); a press queues the click and asks for a manage sequence.
  Only the left button acts on workspace tags, tabs and picker cards; any
  button closes the help.
  Focus-follows-mouse only acts when the pointer actually moved since the
  previous manage sequence, so re-tiling under a still pointer does not steal
  focus. Pointer bindings act on the window under the pointer.
* **Locking.** While river reports the session locked, only bindings without
  modifiers (media keys) run.
* **Signals** use a self-pipe (`signal-hook`), leaving the signal mask that
  spawned children inherit untouched; children run via `sh -c` in their own
  process group and are reaped on `SIGCHLD` (any exited child, so children
  spawned before a restart are reaped too).

== System tray

`[bar] tray = true` (the default) shows `StatusNotifierItem` icons between
the battery and the clock: `Batt: 80% | ▣ ▣ | 2026.10.01-4 13:05`.
`tray_icon_size` (16) is their logical size (`BarStyle::icon_size`).

* **Threading.** `tray::Tray::start` spawns the `oxmonad-tray` thread and
  returns at once: the thread connects to the session bus itself (a missing
  bus only logs a warning; the bar then shows no tray). All D-Bus work runs
  there on a local `async-executor` with `zbus`; calls to items are bounded
  by a timeout, so a hung client never stalls the others, and the main loop
  never waits on D-Bus. The thread reports the full item list over a calloop
  channel (`TrayEvent::Items`, only when it changed); commands go back over
  a non-blocking channel.
* **Watcher and host.** When nobody owns `org.kde.StatusNotifierWatcher`,
  the tray is the watcher too; otherwise (waybar, a desktop shell…) it
  registers as a host with the existing watcher and follows its signals,
  taking the name over if that watcher goes away. Items are followed for
  property, status, icon and dbusmenu layout changes; icons come from
  pixmaps or the icon theme, prepared for twice the logical size (HiDPI).
* **Bar.** `State` keeps the items in `Status::tray` as `tray_ui::BarItem`s,
  each icon converted once to an `oxmonad_ui::Icon` when the list arrives;
  a changed list asks for a manage sequence like the clock does. Passive
  items and items without an icon are not shown (the latter logged at
  debug). Each icon segment's action is the item id, so a click on the
  right side of the bar maps to `Click::TrayItem(id)`. Only the primary bar
  has a right side (`BarModel::primary`), so the tray, its clicks and its
  menu live there. `dump-state` lists every shown bar under `bars` (output
  id and name, rectangle, `primary`, layout, title and `clicks`, the
  workspace tags `{"workspace": tag, "x": [start, end]}` and tray icons
  `{"tray": id, "x": [start, end]}`) and the items, connection and open
  menu under `tray`.
* **Input mapping.** Left click: `Activate(x, y)`, or the menu for
  `ItemIsMenu` items (`ContextMenu(x, y)` if they export no dbusmenu);
  middle: `SecondaryActivate(x, y)`; right: our menu popup, or
  `ContextMenu(x, y)` without a dbusmenu; `x`, `y` are the click's global
  logical coordinates. Wheel clicks (`axis_discrete`) or every 15 units of
  continuous scrolling become `Scroll(delta, "vertical" | "horizontal")`,
  sent straight from the `wl_pointer` frame (they change nothing oxmonad
  manages).
* **Menu surface.** An open menu is `tray_ui::OpenMenu` in `State` (binary
  state: the item, the anchor and one level per open (sub)menu with its
  selection). Each manage sequence rebuilds every level from the item's
  current layout (`OpenMenu::refresh`: invisible entries dropped,
  separators collapsed, toggles mapped to check/radio rows, submenus whose
  entry vanished closed, menus taller than the output's usable area
  truncated), places it and shows it as shell surface `Node::TrayMenu(level)`
  with `Content::TrayMenu`. The root hangs below the icon (above it for a
  bottom bar), clamped into the primary bar output's usable area; a submenu
  cascades to the right of its entry, or to the left when it does not fit.
  Opening sends `AboutToShow(0)`, opening a submenu `AboutToShow(id)`; a
  changed layout arrives as a new item list and refreshes the menu in
  place. Choosing a leaf sends `Event(id, "clicked")` and closes the menu.
* **Focus and closing.** While the menu is open, the seats' keyboard focus
  goes to its root surface instead of core's focus (the `focus` request is
  redirected and resent when the menu opens or closes), so `Escape` and the
  navigation keys reach it. The menu closes on `Escape`, a click outside it
  (a window interaction, any other shell surface; clicking its own icon
  only closes it), any key or pointer binding, when an overlay takes the
  keyboard, when the primary bar is hidden and when its item or menu
  disappears.
  A click on the empty desktop reaches no client and leaves it open.
* **Reload and restart.** `SIGUSR1` starts or stops the tray thread to match
  `[bar] tray` and restarts it when `tray_icon_size` changed. A restart in
  place simply loses the thread and its connection with `exec` (every
  descriptor zbus, `async-io` and calloop open is close-on-exec; the
  end-to-end restart test checks the descriptors with the tray connected to
  a private bus). The new process becomes the watcher again; items show up
  again if they re-register when the watcher's owner changes
  (`NameOwnerChanged`), which libappindicator, KDE and Electron items do.
  An open menu is not preserved.

== Virtual screens

xmonad's `XMonad.Layout.LayoutScreens.layoutSplitScreen` (bound to
`Mod+Shift+s` as `layoutSplitScreen 2 (TwoPane 0.5 0.5)`) and
`XMonad.Actions.PhysicalScreens.rescreen` (`Mod+Ctrl+Shift+s`) as the core
actions `split-screen <n>` and `rescreen`.

* **Outputs vs screens.** Core keeps river outputs (`OutputId`, name,
  rectangle, usable area) separately from screens. A screen covers a
  `region` of its output as a `RationalRect`; its `rect` is the region
  scaled onto the output with every edge floored (so regions that tile the
  output give rectangles without gaps: the left half of an odd width is
  `floor(w/2)`, as `TwoPane`'s `splitHorizontallyBy`), and its
  `usable_rect` is `rect` intersected with the output's usable area
  (layer-shell `non_exclusive_area` is per output). An output's first screen
  is `ScreenId(output)`; the extra virtual screens get ids from 2^32^ up.
  Screen order (xmonad's screen numbering, used by `swap-next-screen` and
  copies) is by output, then region top-to-bottom, left-to-right, so a
  split's screens follow each other like xmonad's renumbering in
  `layoutSplitScreen`. Physical order sorts the virtual rectangles.
* **`split-screen n`** (2 to 16) splits the current screen's region into `n`
  equal columns — for `n = 2` exactly `TwoPane 0.5 0.5`'s halves; xmonad's
  `TwoPane` would give only two screens for any `n`, so equal columns are
  the generalisation. Like `layoutSplitScreen`, the current screen keeps
  its workspace on the leftmost column and stays current; the new screens
  take the first hidden workspaces in order (most recently hidden first,
  never `NSP`). Where xmonad would leave part of the output without a
  screen when too few workspaces are hidden, oxmonad creates fresh
  workspaces (like a new output does). Splitting a virtual screen splits
  its region again.
* **`rescreen`** gives each output one screen covering it. On each output
  the current screen, else its first screen, survives with its workspace
  (and takes `ScreenId(output)` again); the workspaces of the other screens
  become the most recently hidden ones in screen order — xmonad's
  `map workspace visible ++ hidden`. Unsplit outputs keep their workspace
  (PhysicalScreens' same-count case). Deviation: xmonad's core `rescreen`
  would put the current workspace on the first physical screen; oxmonad
  keeps it on its own output.
* **Output changes.** A changed output rectangle rescales its screens'
  regions (a split keeps its proportions); a removed output removes all its
  screens, their workspaces becoming the most recently hidden in screen
  order; a new output gets one screen.
* **Bar.** A split output has one bar spanning its usable width; every
  screen on it tiles below (or above) the bar strip, and the dividers run
  from the bar to the other edge of the usable area. The bar shows the
  layout and title of the current screen if it is on that output, else of
  the output's first screen, and follows that workspace's `toggle-bar`.
* **Dividers.** `[split] divider_width` (default 3, `0` for none),
  `divider_color` (default `#1E88E5`) and `divider_padding` (default 2). `divider::divide` (pure) takes the
  tiling areas of one output's screens without dividers (usable rectangle
  minus the bar) and, for every pair that shares an edge (one ends exactly
  where the other starts, along x for side-by-side screens or along y for
  stacked ones; `split-screen` only makes columns, but the rule is
  general) and overlaps along it, puts a strip `divider_width` wide
  centred on the edge, spanning that overlap (so it starts below the bar
  and stays inside the layer-shell usable area). The screen on the left
  (top) gives up `floor(w/2)` of its tiling area, the one on the right
  (below) `ceil(w/2)`: an odd width puts the extra pixel on the right
  (lower) side. Each also gives up `divider_padding` more, left empty so
  window borders keep clear of the line (none without a divider). A screen with several neighbours on one side gives the
  space up once. `Wm::tiling_area` is the divided area, so tiled windows
  never sit under a divider; `Screen.rect`/`usable_rect` stay unchanged,
  so floats (placed relative to `rect`), the prompt, picker and help, and
  a `VirtualFullscreen` window (the full `rect`) ignore the dividers.
  Only screens of the same output are paired: no divider on an output's
  outer edges, between two outputs or on an unsplit output, and
  `rescreen` removes them. A reload applies new values at once.
  `dump-state` lists them under `dividers` (`{"output": id, "rect":
  [x, y, w, h]}`) and their surfaces under `shells`.
* **Fullscreen.** river's `fullscreen(output)` covers the whole output, so a
  window fullscreen on a virtual screen gets `Layer::VirtualFullscreen`:
  the binary proposes the screen's rectangle, places it like a float
  stacked with the fullscreen windows (above the bar) and only sends
  `inform_fullscreen`. On unsplit outputs `Layer::Fullscreen` uses river's
  fullscreen as before; `rescreen`/splitting switches between the two.
* **Restart.** The snapshot stores each screen's region; `finish_restore`
  splits an output (matched by name) the same way before assigning
  workspaces. A split output that does not come back is dropped.

== Restart in place

`restart` (`Mod+q`) replaces the running oxmonad with the binary now at the
path it was started from, keeping every window where it was — xmonad's
`restart`, which serializes the `WindowSet` and resumes it in the new
process.

It relies on three properties of river 0.4.8, verified with a headless
river:

. When the window manager sends `stop`, receives `finished`, destroys its
  objects and disconnects, river keeps running and keeps every window
  alive. Before `finished` river sends `closed` for every window and
  `removed` for every output and seat; oxmonad ignores those.
. A newly bound `river_window_manager_v1` receives `output` (with position
  and dimensions), `seat` and `window` events (with `identifier`, `app_id`
  and `title`) for everything that exists, all before its first
  `manage_start`. `wl_output`s are bound before the window manager, so
  their names are known by then too.
. `river_window_v1.identifier` is stable across window-manager reconnects
  (and unique, never reused).

The sequence:

. Core turns `Action::Restart` into `Effect::Restart`. After the manage
  sequence, the binary runs `<binary> --check-config` (with the original
  arguments); if that fails (binary missing, broken, or an invalid config)
  it logs the error and carries on as if nothing happened.
. It takes `Wm::snapshot` — a serde `Snapshot` (with a `version`) of the
  workspaces in xmonad order with their layout rings (each layout's state),
  window order and focus, which workspace each screen (by output name)
  shows and the region of its output it covers (so splits survive), the
  current workspace, floating rectangles, fullscreen windows and the
  per-workspace bar toggles (which then decide every output's bar), naming windows by river identifier — and sends `stop`. Snapshots
  without regions (written before splits existed) load as unsplit, so the
  format version stayed 1.
. On `finished` it answers pending control commands, destroys every
  window-management object, writes the snapshot to
  `$XDG_RUNTIME_DIR/oxmonad-restart-<pid>.json` and `exec`s the binary path
  resolved at startup (`/proc/self/exe` would point at the replaced, deleted
  inode after a rebuild) with the original `argv` plus
  `OXMONAD_RESTORE=<file>`. The pid stays the same, so river does not
  notice its child exiting; every descriptor oxmonad opens is close-on-exec
  (Wayland socket, epoll, signal self-pipes, control socket, memfds), and
  the new process rebinds the control socket.
. The new process reads and deletes the file (an unreadable or incompatible
  snapshot is logged and ignored), loads the configuration, calls
  `Wm::restore`, binds the window manager and manages the announced windows
  with `Wm::manage_as(id, identifier, info)`: a window the snapshot knows
  goes back to its workspaces, floating or fullscreen, without manage
  rules; others are managed normally. At the end of the first manage
  sequence `Wm::finish_restore` restores each workspace's window order and
  focus, splits each output (by name) the way it was split and the
  screens' workspaces (matched by output name, then by order), and forgets
  windows that did not come back.
. If `exec` itself fails after the check passed, the old process restores
  the snapshot into a fresh `Wm` with the configuration reloaded and binds
  the window manager again on its existing connection.

Not preserved: an open prompt, layout picker, help or tray menu, a pointer move/resize in progress, and
xmonad's workspace history beyond the hidden-workspace order. A layout ring
whose layouts changed between the two binaries or in the config's `layouts`
(reordered or shortened) falls back to the configured ring (keeping the
active layout if it still exists). river keeps
fullscreen windows fullscreen and does not report their dimensions to the
new window manager again, so their size is unknown until they change.
